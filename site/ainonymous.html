HybridNode : une architecture à trois couches

AInonymous ne se limite pas à un simple réseau P2P. HybridNode combine SD-WAN, Holochain et QUIC/mTLS pour distribuer l'inférence en tenant compte de la topologie réseau.

CoucheTechnologieRôle
OverlayHolochain 0.6.1DHT, identité (AgentPubKey ed25519), coordination
Plan de donnéesQUIC / mTLSTransfert des activations tensorielles, flux de tokens
UnderlaySD-WANRoutage conscient de la topologie, SLA, QoS
🔒

mTLS strict

La clé AgentPubKey ed25519 sert de certificat QUIC ; PeerKeyVerifier impose l'authentification mutuelle.

🧬

Attestation de modèle

Vérification SHA-256 locale, confirmée par au moins 2 pairs du réseau.

⚠️

Système de mandats (warrants)

Preuve cryptographique de mauvais comportement stockée dans le DHT Holochain ; exclusion automatique du scheduling.

🔐

Bootstrap privé

Membrane PrivateNetworkProof pour les déploiements en consortium fermé.

Réseau fermé

Mode privé : l'opposé du mesh public

Par défaut, AInonymous est un mesh public et anonyme — n'importe qui rejoint le DHT sans autorisation. HybridNode permet aussi l'inverse : un réseau fermé, où l'admission exige une preuve cryptographique (Membrane Proof) signée par un administrateur — pour un consortium d'entreprise multi-sites, un groupement de recherche, ou tout déploiement où le contrôle d'accès prime sur l'ouverture.

Composant du mode privéStatut réel
MembraneProofConfig + injection automatique dans les appels de zome✓ codé et fonctionnel
Admission gate dans le zome d'intégrité (feature private-network)✓ vérifie la signature ed25519 de la preuve contre la clé d'administrateur réseau configurée dans dna.yaml
Installation d'une hApp avec preuve, côté conducteur✗ non fonctionnel actuellement (API holochain_client changée)
Expiration / anti-rejeu de la preuve✗ champ présent, non vérifié — pas d'accès horloge vérifié dans HDI
Proof-of-work à l'admission, liste blanche d'agents✗ pas implémenté — architecture cible uniquement

Direction d'architecture réelle et partiellement codée, pas une fonctionnalité clé-en-main — la vérification cryptographique de la preuve à l'admission reste le chaînon manquant avant un déploiement en consortium fermé.

Advanced architecture

HybridNode: a three-layer architecture

AInonymous isn't just another P2P network. HybridNode combines SD-WAN, Holochain, and QUIC/mTLS to schedule inference with full network-topology awareness.

LayerTechnologyRole
OverlayHolochain 0.6.1DHT, identity (AgentPubKey ed25519), coordination
Data planeQUIC / mTLSTensor activation transfers, token streams
UnderlaySD-WANTopology-aware routing, SLA enforcement, QoS
🔒

Strict mTLS

The ed25519 AgentPubKey is reused as the QUIC certificate; PeerKeyVerifier enforces mutual authentication.

🧬

Model attestation

SHA-256 verified locally, confirmed by at least 2 peers on the network.

⚠️

Warrant system

Holochain DHT cryptographic proof of misbehavior; automatically excludes the peer from scheduling.

🔐

Private bootstrap

PrivateNetworkProof membrane for closed consortium deployments.

Closed network

Private mode: the opposite of the public mesh

By default, AInonymous is a public, anonymous mesh — anyone can join the DHT without authorization. HybridNode also supports the opposite: a closed network where admission requires a cryptographic proof (Membrane Proof) signed by an administrator — for a multi-site enterprise consortium, a research group, or any deployment where access control matters more than public openness.

Private mode componentActual status
MembraneProofConfig + automatic injection into zome calls✓ coded and working
Admission gate in the integrity zome (private-network feature)✓ verifies the proof's ed25519 signature against the network admin key configured in dna.yaml
Installing a hApp with a proof, conductor-side✗ currently non-functional (holochain_client API changed)
Proof expiration / replay protection✗ field present, not yet checked — no verified clock access in HDI
Proof-of-work at admission, trusted-agent allowlist✗ not implemented — target architecture only

A real, partially-coded architecture direction, not an off-the-shelf feature yet — cryptographic verification of the admission proof is the missing link before any closed-consortium deployment.

Pourquoi une boucle fermée change tout

Dans un déploiement public, vos données traversent des serveurs tiers — anonymisées ou non. Dans la boucle fermée AInonymous, la question d'un collaborateur ne quitte jamais votre LAN ou VPN d'entreprise.

La Distributed Hash Table (DHT) Holochain tourne à l'intérieur de votre infrastructure. Les nœuds se découvrent mutuellement par votre réseau interne, et les échanges sont chiffrés de bout en bout par des clés ed25519 propres à chaque machine.

  • ✓Découverte de nœuds : via le réseau d'entreprise (pas de relais externe Nostr ou public)
  • ✓Transport : WebRTC sur LAN ou QUIC sur VPN — pas d'internet requis
  • ✓État partagé : source chain Holochain immutable, auditée, locale
  • ✓Identité : Membrane Proofs pour contrôler qui rejoint le réseau privé
  • ✓Air-gap possible : fonctionne sur réseau isolé sans accès internet

Prompt utilisateur

L'utilisateur envoie une requête via son outil (VS Code, chat interne, n8n…)

2

API proxy locale

Le proxy :9337 reçoit la requête OpenAI-compat. et l'envoie au conducteur Holochain

3

Routage DHT

Le mesh consulte le registre des nœuds pour trouver les machines disponibles selon le modèle et la charge

4

Inférence distribuée

Les couches du modèle sont exécutées en pipeline sur les nœuds sélectionnés (layer-sharding)

5

Streaming tokens

Les tokens générés sont streamés vers l'API en temps réel — latence identique à du local

6

Audit chain

La tâche est chainée cryptographiquement pour traçabilité. Aucune donnée sensible stockée.

Why a closed loop changes everything

In a public deployment, your data travels through third-party servers — anonymized or not. In the AInonymous closed loop, an employee's query never leaves your corporate LAN or VPN.

The Holochain Distributed Hash Table (DHT) runs inside your infrastructure. Nodes discover each other through your internal network, and all exchanges are end-to-end encrypted with ed25519 keys unique to each machine.

  • ✓Node discovery: via the corporate network (no external Nostr or public relay)
  • ✓Transport: WebRTC over LAN or QUIC over VPN — no internet required
  • ✓Shared state: immutable, audited, local Holochain source chain
  • ✓Identity: Membrane Proofs to control who joins the private network
  • ✓Air-gap capable: works on isolated network with no internet access

P2P Infrastructure

Functional model

How a request traverses the network

From your employee's prompt to the response — without ever touching the outside world.

1

User prompt

The user submits a request via their tool (VS Code, internal chat, n8n…)

2

Local API proxy

The :9337 proxy receives the OpenAI-compat. request and forwards it to the Holochain conductor

3

DHT routing

The mesh consults the node registry to find available machines by model and current load

4

Distributed inference

Model layers are executed in pipeline across selected nodes (layer-sharding)

5

Token streaming

Generated tokens stream to the API in real time — latency identical to local execution

6

Audit chain

The task is cryptographically chained for traceability. No sensitive data stored.

Security & compliance

Built for the most demanding
environments.

Every layer of the system is designed to satisfy the requirements of CISOs, DPOs, and security teams.

🔑

Cryptographic identities

Every node is identified by an ed25519 key pair. No centralized authentication, no password — cryptography is the sole identity mechanism.

ed25519 · Holochain keys
🚪

Network access control

Membrane Proofs define who can join the private network. A machine without a valid proof is invisible to the mesh — even on the same LAN.

Membrane Proofs · RBAC
🔒

End-to-end encryption

All inter-node exchanges are encrypted. Data in transit is protected even on a compromised internal network.

TLS · WebRTC DTLS · E2E
📋

Immutable audit trail

Every inference task is appended to a Holochain source chain — a cryptographically linked append-only structure. Ideal for regulatory audits.

Source chain · append-only
🌐

Full network isolation

The network can run without any internet access. Supported modes: internal LAN, corporate VPN, air-gapped network. Zero dependency on external relays or DNS.

Air-gap ready · VPN · LAN
🔍

Peer validation

Holochain validation zomes allow each node to verify the conformity of other nodes' data before accepting it. No undetected malicious node.

Zome validation · warrants
